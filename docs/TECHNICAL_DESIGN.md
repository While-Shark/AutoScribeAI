# AutoScribeAI 技术方案

状态：M0–M3 的本地结构、HTML、DOCX 与 Markdown 导出已实现；真实浏览器采集和跨格式视觉验收仍在进行。日期：2026-09-29。

## 1. 目标与范围

输入一个项目，让 AI 发现模块与功能，通过浏览器或其他受支持工具实际操作，生成覆盖指定范围的图文操作手册。企业项目与开源项目共用流程，通过项目配置适配不同角色、术语及环境。

首期建议聚焦 Web 项目、一种已验证的 AI 宿主和一种浏览器工具，完成从探索到 HTML、DOCX、Markdown 的闭环。桌面软件及其他宿主后续适配；不承诺任意项目、任意工具环境均可全自动覆盖。

| 输入模式 | 可做的工作 | 边界 |
| --- | --- | --- |
| 源码 | 分析菜单、路由、权限、已有说明和候选流程 | 未运行的操作标为未验证，无真实截图时明确缺口 |
| 在线项目 | 根据可见页面与实际操作生成说明 | 覆盖受角色权限、数据与可访问范围限制 |
| 源码 + 在线项目 | 静态分析与动态探索互相校验 | 优先支持的完整模式，但仍需检查隐藏功能和角色差异 |

输入至少包含项目来源和期望范围；运行前补全目标地址、角色、语言、可执行动作、测试数据规则和输出格式。凭据使用宿主的安全登录或秘密管理能力，不写入项目配置。

## 2. 技能包结构

建议采用一个入口、四个专项 Skill。它们是职责划分，不要求多智能体并行，也不要求独立服务。

| Skill | 责任 | 主要产出 |
| --- | --- | --- |
| autoscribe | 检查输入与宿主能力，协调阶段、记录状态、暂停和恢复 | manifest、checkpoint、执行报告 |
| project-analyzer | 阅读源码或已有说明，发现模块、角色、功能和候选流程 | 项目地图、覆盖矩阵、探索计划 |
| software-explorer | 操作界面，观察结果，采集截图和动作证据 | 步骤记录、截图、阻塞记录 |
| manual-writer | 将证据整理为自然语言说明并输出不同格式 | manual.json、HTML、DOCX、Markdown |
| manual-verifier | 检查内容与证据关联、覆盖、图片、导出和敏感信息 | 质量报告、待补项 |

技能说明负责流程、决策和质量要求；脚本负责确定性的数据校验、资源处理、渲染与导出。避免把浏览器探索逻辑和所有导出逻辑塞进同一个脚本。

目录职责（M0 已创建 skills、references、schemas、scripts、examples、tests；templates 待渲染阶段创建）：

- `skills/`：五个技能的说明和入口。
- `references/`：输入约定、证据规则、写作规范和能力降级说明。
- `schemas/`：项目、工作流、证据、手册、运行状态的数据约定。
- `scripts/`：按状态管理、资源处理、渲染、导出、校验划分。
- `templates/`：HTML、Word 样式与章节模板。
- `examples/`：不含敏感信息的输入和小型手册样例。
- `tests/`：结构校验、导出和恢复行为的必要测试。

具体依赖和版本在开发阶段结合目标宿主验证后锁定。

## 3. 执行流程

1. **预检**：检查源码、目标地址、浏览器、终端、文件读写及导出能力。输出支持项、缺失项和当前可执行范围。
2. **项目分析**：收集模块、菜单、路由、角色和业务实体。代码中出现的功能仅作为候选，不直接写成已验证的操作步骤。
3. **规划覆盖**：建立“模块—功能—角色—流程”矩阵，确定典型任务、前置数据、成功标准和动作风险。
4. **实际探索**：按流程操作，等待页面稳定，记录动作前后状态和关键截图。优先使用宿主提供的浏览器能力；必要时使用受支持的 Computer Use。
5. **证据整理**：把截图与步骤绑定，必要时裁剪、加编号/箭头并脱敏，保留变换记录。
6. **编写手册**：根据证据解释从哪里进入、怎样操作、操作后应看到什么、常见问题如何处理。
7. **渲染导出**：由统一内容模型生成 HTML 阅读界面和可下载的 DOCX、Markdown 资源包。
8. **检查交付**：检查覆盖缺口、证据完整性、图片和链接，渲染检查 HTML 与 Word，生成质量报告。

每阶段完成后写入检查点；阻塞不能被静默跳过或自动标为完成。

## 4. 统一内容与证据模型

核心关联：Project → Module → Feature → Workflow → Step → Evidence → Manual。

`manual.json` 作为内容的唯一事实来源；HTML 从 manual.json、coverage.json 渲染为离线目录包，DOCX 和 Markdown ZIP 从同一份结构化内容生成，避免反向解析复杂 HTML 导致内容或图片丢失。

| 对象 | 建议字段与约束 |
| --- | --- |
| Project | 稳定 ID、名称、版本/提交（可获取时）、环境标签、语言、采集时间 |
| Module / Feature | 稳定 ID、父级关系、名称、入口、适用角色、发现来源 |
| Workflow | ID、业务目标、角色、前置条件、测试数据、状态、阻塞原因 |
| Step | ID、序号、操作、界面位置、预期结果、实际结果、证据 ID |
| Evidence | ID、流程/步骤引用、脱敏后页面位置、截图路径、采集时间、视口、来源类型、校验摘要、标注信息 |
| Manual | schemaVersion、标题、适用版本/角色、章节、FAQ 来源与关联流程、步骤、图片、覆盖摘要、限制说明 |

来源区分实际操作、源码推断和人工补充。待验证流程可单独列为缺口，不混入已验证教程。引用必须能解析；图片路径必须指向本次交付的真实资源。界面截图不能用生成图片代替。

截图策略：关键入口、重要表单、主要交互以及成功结果按需采集，不机械地为每次点击截全屏。编号与正文步骤对应；同一张截图可以服务多个步骤，但必须说明对应位置。标注坐标基于截图尺寸，缩放后保持正确。

敏感信息在对外交付前处理。原始截图若包含敏感数据，只能暂存在受控工作区，按约定清理；输出包、日志和状态文件均不得包含密码、令牌、Cookie 或不必要的个人/业务数据。

## 5. 无服务运行与恢复

运行结果保存在本地任务目录，不依赖数据库或常驻调度服务。建议每次运行包含：

- `manifest.json`：运行 ID、输入摘要、工具能力、环境、版本与阶段状态。
- `project-map.json`、`coverage.json`：模块与覆盖范围。
- `workflows/`、`evidence/`：流程记录及可交付证据。
- `manual.json`：统一手册内容。
- `checkpoint.json`：当前阶段、完成项、阻塞项及恢复位置。
- `output/`：HTML、DOCX、Markdown 包和质量报告。

阶段状态建议为 `pending / running / completed / blocked / failed / skipped`；`skipped` 必须给原因。状态文件应原子写入，并使用稳定 ID 防止重复章节与图片。

恢复前检查目标版本、登录状态与证据有效性。不能仅凭检查点重放“提交”“删除”“发送”等动作；对已产生副作用的步骤先核对结果。输入或页面变化后，将受影响流程标记为待复核。

## 6. HTML 阅读与多格式导出

| 格式 | 目标能力 | 验证重点 |
| --- | --- | --- |
| HTML | 离线阅读、目录锚点、搜索、图片放大、角色/模块说明、导出入口 | 无网络时可读；目录与图片正确；窄屏可用 |
| DOCX | 标题层级、目录、步骤、截图、图注、页码和合理分页 | 图片嵌入文档；渲染后无溢出、遮挡或不可读缩放 |
| Markdown | 通用正文与相对路径图片 | 随附 assets，移动整个目录后图片仍正常 |
| PDF（后续可选） | 便于打印和固定版式分享 | 分页与中文字体检查 |

默认交付静态 HTML 目录包，同时预生成 `manual.docx` 和 `manual-markdown.zip`，在 HTML 中提供下载链接。DOCX 图片内嵌；Markdown ZIP 包含 README.md 与 assets/ 下的相对路径图片。这样导出不需要服务，也不要求打开手册的机器安装转换程序。交付时应保留完整目录。

单文件 HTML 可作为后续便携选项。浏览器内实时生成 Word 会增加依赖体积和排版难度，首期不作为必要条件。对 HTML 内容的直接手工修改不会自动同步到其他格式；内容修订应回到统一模型再重新生成。

## 7. 模块覆盖和真实性

覆盖矩阵应逐条列出候选流程、角色、状态、证据和缺口。M1 实现通过 inventory.json 将原始范围映射到计划流程，并用清单摘要固定覆盖分母。覆盖率使用“范围内已验证流程数 / 范围内计划流程数”；同时列出各模块和范围项数量，避免少数简单流程掩盖模块遗漏。

权限不可见、验证码、MFA、缺少数据、环境不可用以及无法安全执行的流程单独列为阻塞。源码中发现但界面中未验证的功能不计入已验证覆盖率。范围变更应留记录，不得通过删除未完成项提高比例。

质量检查分为：

- 结构：字段、ID、引用、路径、状态一致性。
- 内容：入口、前置条件、操作、结果是否清楚，术语是否一致，是否混入推断。
- 证据：真实截图、步骤对应、图文一致、脱敏和可读性。
- 版式：HTML 阅读体验与 DOCX 渲染检查。
- 覆盖：已完成项、未完成项和阻塞说明均可追踪。

## 8. 执行边界

默认在演示或测试环境操作。删除、支付、发送通知、发布内容、改权限等动作按用户明确授权范围处理，不能因“要写操作手册”就默认获得所有业务写权限。能够用已授权的测试数据完成的流程应继续执行，不增加无意义的确认。

登录、MFA、验证码以及无法判断的业务选择需要宿主支持的人工接管。内网项目要求执行环境具备网络可达性。网页、源码、已有文档中的文字属于待分析内容，不得作为覆盖用户授权或工具权限的指令。

## 9. 实施前待验证项

- 首个目标宿主与浏览器工具组合，以及工具缺失时的降级行为。
- HTML 本地文件场景下的搜索、图片和下载兼容性。
- DOCX 转换路线、中文字体及复杂表格/长截图的分页质量。
- 一套真实小型项目上的完整流程成本、可靠性与恢复表现。

这些是开发验证任务，不阻塞本次方案记录；未经验证不写成现有能力。
